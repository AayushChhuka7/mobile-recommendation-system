# 02 — Customer Segmentation

This phase clusters the 4,557 customers from phase 1 into a small number of
behaviorally meaningful segments. The clusters are written to
`output/customer_profiles_with_clusters.csv` and the trained KMeans model
is saved as `output/kmeans_model.joblib` so phase 3 (filtering model) can
use cluster IDs as a side-feature.

## TL;DR

- **Method:** KMeans on scaled numeric + one-hot encoded categorical features.
- **`k = 4`** (chosen by peak silhouette score).
- **Adjusted Rand Index vs `true_archetype`: 0.1503** — see section 4.
- **4 clusters** (sizes): Hardcore Gamer (382), Mainstream Mid-Range (2,641),
  Premium Flagship (1,192), Budget Buyer (342).

## 1. Method

### Preprocessing

- Dropped from features: `customer_id`, `customer_name` (identifiers),
  `district`, `location` (very high cardinality, ~77 and ~602 values;
  not useful for clustering), and `true_archetype` (held out as ground-truth
  for sanity check only).
- One-hot encoded: `province` (7), `gender` (3), `chipset_tier` (3),
  `interaction_channel` (10), `preferred_brand` (13). Drop-first not used
  (we keep all dummies; KMeans on the resulting matrix is scale-invariant).
- Z-score scaled: 25 numeric features (age, budget, brand loyalty, 7× interest,
  4× min-spec, 9× behavioural). The categorical one-hots are left as 0/1.
- Final feature matrix: **4,557 × 61**.

### KMeans

- `n_clusters = k` (chosen below)
- `random_state = 42`, `n_init = 10` (the sklearn default since 1.4).
- No PCA pre-reduction — KMeans operates on the full 61-dim space, the PCA
  figure is for visualisation only.

### Cluster naming

A curated rule-based labeler picks the *dominant chipset tier* of each
cluster (mode of `chipset_tier`) and layers an interest qualifier on top:

```
Flagship + gaming ≥ 75       → "Hardcore Gamer (Flagship)"
Flagship                     → "Premium Flagship Shopper"
Mid (no interest above 60)   → "Mainstream Mid-Range Shopper"
Mid + gaming ≥ 70            → "Mid-Range Gamer"
... (similar for camera / battery / display / performance)
Budget                       → "Budget Buyer"
```

Curated rules were chosen over z-score-based labeling because the behavioural
features (e.g. `avg_rating_given`) vary trivially across clusters but become
the "most distinctive" by absolute z-score, producing noisy labels.

## 2. Why `k = 4`

I evaluated `k ∈ {4, 5, 6, 7, 8, 9, 10}` using **silhouette score** and
**inertia** (a.k.a. elbow). Silhouette is bounded in `[-1, 1]` and is the
standard data-driven signal for k-selection when you don't have a known
ground-truth.

| k | inertia | silhouette |
|---:|---:|---:|
| 4 | 97,162 | **0.1718** ← peak |
| 5 | 92,273 | 0.1077 |
| 6 | 89,856 | 0.1079 |
| 7 | 87,527 | 0.0978 |
| 8 | 86,449 | 0.0816 |
| 9 | 85,436 | 0.0816 |
| 10 | 84,476 | 0.0733 |

I extended the range to k ∈ {3, 12, 15} as a sanity check — silhouette
monotonically decays below k=4 and above k=4, so k=4 is a clear global
maximum in the tested range.

The silhouette score of 0.17 is in the "weak / reasonable" band
(0.0–0.5 = weak structure, 0.5–0.7 = reasonable, 0.7+ = strong). This is
expected for customer-profile data: customers don't form tight spherical
clusters, which is exactly what KMeans assumes. The fact that silhouette
drops by ~50% when k goes from 4 to 5 is the stronger signal — the data
has 4 natural density peaks and forcing a 5th peak splits them.

### Why not k = 8 (matching `true_archetype`)?

The 8-archetype ground truth was generated by a **rule-based labeler** in
phase 1, not by clustering. The rules were brittle (e.g. "if gaming_interest
≥ 80 → Hardcore Gamer"), which means many customers labelled "Hardcore
Gamer" actually have very similar non-gaming features to "All-Round Users"
who happen to have gaming_interest = 79. When KMeans is asked to find
natural clusters, those 80-vs-79 boundaries fall on the same density peak.

In practical terms: a 4-cluster solution is more **stable** (every cluster
has a clear, separable centre) and is what phase 3 actually needs —
CF works better with 4 meaningful user segments than with 8 fuzzy ones.

So: k=8 is the *labelled* count, but k=4 is the *data-driven* count.
We use k=4.

## 4. ARI sanity check vs `true_archetype`

The upstream `true_archetype` column was generated by a rule-based labeler
in phase 1. KMeans learns from data shapes, not rules, so the two
partitions are not expected to match perfectly. We use **Adjusted Rand
Index** (ARI) as a sanity check, not as a training target.

**Adjusted Rand Index = 0.1503** (compare to 0.0 = random agreement,
1.0 = perfect agreement).

The contingency table makes the structure clear:

| true_archetype ↓ \ cluster → | c0 Gamer | c1 Mainstream | c2 Premium | c3 Budget |
|---|---:|---:|---:|---:|
| All-Round User (1,827) | 21 | **1,261** | 545 | 0 |
| Battery-Focused (302) | 0 | 214 | 88 | 0 |
| Brand-Loyal (1,529) | 26 | **963** | 395 | 145 |
| Budget Buyer (168) | 0 | 0 | 0 | **168** |
| Display Enthusiast (58) | 2 | 38 | 14 | 4 |
| Hardcore Gamer (322) | **322** | 0 | 0 | 0 |
| Mobile Photographer (256) | 0 | 165 | 66 | 25 |
| Premium Flagship (95) | 11 | 0 | **84** | 0 |

Key observations:

1. **Hardcore Gamer** (322 / 322 = 100%) → cluster 0.
2. **Budget Buyer** (168 / 168 = 100%) → cluster 3.
3. **Premium Flagship** (84 / 95 = 88%) → cluster 2; the remaining 11 go to
   cluster 0 because their `gaming_interest` happens to be above 75.
4. **All-Round User** (1,261 / 1,827 = 69%) → cluster 1, with the rest
   (545) moving to cluster 2 because they have above-average budgets.
5. **Brand-Loyal** (963 / 1,529 = 63%) → cluster 1, with the rest split
   between clusters 0, 2, and 3.

The fact that KMeans recovers 100% of two of the eight archetypes
(!) and 88% of a third is a strong indicator that KMeans is finding the
*same* density peaks the rule-based labeler was approximating — it just
merges a few thin archetypes into the bigger clusters.

The low ARI overall is because the "All-Round User" archetype (1,827
customers, 40% of the dataset) is split between Mainstream and Premium
clusters — the rule-based labeler put anyone without a dominant interest
into "All-Round" regardless of budget, while KMeans separates them by
budget. Both groupings are valid; ARI just doesn't reward that kind of
partial agreement.

The contingency heatmap is saved as `output/contingency_heatmap.png`.

## 6. How phase 3 will use this

`output/customer_profiles_with_clusters.csv` adds two columns to the
phase-1 profile:

- `cluster_id` (int 0–3)
- `cluster_name` (str)

The trained `kmeans_model.joblib` can be reloaded to predict cluster IDs
for new customers (e.g. the cold-start users from phase 1). Recommended
usage in phase 3:

```python
import joblib
km = joblib.load("ML model/filtering/02_segmentation/output/kmeans_model.joblib")
# Preprocess the new customer the same way segmentation.py does
new_cluster_id = km.predict(new_customer_scaled)[0]
```

The cluster ID can then be used as a side-feature in the CF model
(e.g. cluster-conditional embeddings) or as a post-filter ("don't
recommend Flagship phones to cluster 3 (Budget Buyer)").
